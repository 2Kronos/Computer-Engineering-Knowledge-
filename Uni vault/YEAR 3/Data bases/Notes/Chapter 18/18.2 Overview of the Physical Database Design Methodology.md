### **18.2 Overview of the Physical Database Design Methodology**

#### **Summary**

This section provides a high-level roadmap for the physical database design phase, outlining its eight key steps. This phase directly follows the conceptual and logical design phases, which are Steps 1 and 2 of the overall methodology.

**Definition: Physical Database Design**
The process of producing a description of the implementation of the database on secondary storage. It describes the base relations, file organizations, indexes, integrity constraints, and security measures needed for efficient data access.

**The Eight Steps of Physical Database Design:**

1.  **Step 3: Translate Logical Data Model for Target DBMS**
    *   **Objective:** Convert the DBMS-independent logical model into a implementation-ready form for a specific DBMS (e.g., Oracle, SQL Server).
    *   **3.1 Design Base Relations:** Define the exact SQL data types, constraints (NOT NULL, DEFAULT), and domains for each table.
    *   **3.2 Design Representation of Derived Data:** Decide whether to pre-store calculated data (like totals or counts) or calculate it on-the-fly for better performance.
    *   **3.3 Design General Constraints:** Implement complex business rules that go beyond standard keys and data types using CHECK constraints or triggers.

2.  **Step 4: Design File Organizations and Indexes (The Core of Performance Tuning)**
    *   **Objective:** Determine how data is physically stored and accessed to maximize efficiency.
    *   **4.1 Analyze Transactions:** Understand the most frequent and critical database operations (queries, updates) to identify performance needs.
    *   **4.2 Choose File Organizations:** Select the physical storage structure for each table (e.g., Heap, B+-tree, Hashing). *Note: Many PC DBMSs hide this choice, while enterprise systems offer more control.*
    *   **4.3 Choose Indexes:** Create optimal indexes to speed up query performance without overly slowing down data updates.
    *   **4.4 Estimate Disk Space Requirements:** Forecast the amount of storage space needed for the database.

3.  **Step 5: Design User Views**
    *   **Objective:** Implement the customized views for different users (e.g., managers, staff) that were identified during requirements analysis, often using SQL `CREATE VIEW`.

4.  **Step 6: Design Security Mechanisms**
    *   **Objective:** Implement security measures like access controls and permissions to protect data from unauthorized access.

5.  **Step 7: Consider the Introduction of Controlled Redundancy (Denormalization)**
    *   **Objective:** *Carefully* and selectively introduce redundancy (by deliberately breaking normalization rules) to improve performance for critical transactions. This is a trade-off between speed and data consistency.

6.  **Step 8: Monitor and Tune the Operational System**
    *   **Objective:** An ongoing process after the database is live. Continuously monitor system performance, identify bottlenecks, and make adjustments to the design as data and usage patterns change.

**Key Principle: Physical Data Independence**
A core concept enforced during this process is that the user's view of the data (the logical model) remains unchanged and unaffected by these underlying physical storage decisions. The DBMS handles the mapping between the logical and physical layers through its internal schema.
