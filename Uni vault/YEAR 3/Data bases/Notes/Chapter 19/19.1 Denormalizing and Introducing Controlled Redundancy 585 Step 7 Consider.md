### **Step 7: Consider the Introduction of Controlled Redundancy (Denormalization)**

**Objective:** To determine whether introducing redundancy in a controlled manner by relaxing the normalization rules will improve the performance of the system.

*   **The Trade-off:** Normalization minimizes redundancy for integrity and flexibility, but can sometimes hinder performance. Denormalization is the process of strategically accepting some redundancy to speed up read-heavy queries.
*   **When to Consider:** **Only** if the system is predicted to fail its performance requirements. It is a last resort, not a substitute for good logical design.
*   **Key Considerations:**
    *   Denormalization makes implementation more complex.
    *   It sacrifices flexibility.
    *   It **speeds up retrievals but slows down updates**.
    *   It should be considered primarily for relations with a **low update rate and a very high query rate**.

The text details seven common denormalization techniques, illustrated with the DreamHome case study:

1.  **Step 7.1: Combining One-to-One (1:1) Relationships**
    *   **Example:** Combine the `Client` and `Interview` relations into a single `ClientInterview` relation.
    *   **Benefit:** Eliminates a join for queries needing data from both entities.
    *   **Drawback:** Can lead to many NULL values if the relationship is optional (e.g., clients who haven't had an interview), wasting storage space.

2.  **Step 7.2: Duplicating Non-Key Attributes in 1:* Relationships**
    *   **Example:** Duplicate the owner's last name (`lName`) from the `PrivateOwner` (parent) relation into the `PropertyForRent` (child) relation.
    *   **Benefit:** Removes the need to join to `PrivateOwner` for queries that need the property and the owner's name.
    *   **Drawback:** If the owner's name changes, it must be updated in multiple places (every property they own), risking inconsistency.

3.  **Step 7.3: Duplicating Foreign Key Attributes in 1:* Relationships**
    *   **Example:** Add the `branchNo` attribute directly to the `PrivateOwner` relation.
    *   **Benefit:** Allows a query like "list all owners at branch B003" to run on a single table instead of joining `PrivateOwner` with `PropertyForRent` to find the branch number.
    *   **Drawback:** Only works if the relationship is factually correct (an owner is associated with a single branch). Complicates the schema and requires additional foreign key constraints.

4.  **Step 7.4: Duplicating Attributes in *:* Relationships**
    *   **Example:** Duplicate the `street` attribute from the `PropertyForRent` relation into the intermediate `Viewing` relation.
    *   **Benefit:** For a query needing client and property street data from a viewing, it eliminates the need to join with the `PropertyForRent` table.
    *   **Drawback:** Increases the size of the intermediate table and must be kept consistent if the source attribute changes.

5.  **Step 7.5: Introducing Repeating Groups**
    *   **Example:** Instead of a separate `Telephone` table, store up to three phone numbers directly in the `Branch` table (`telNo1`, `telNo2`, `telNo3`).
    *   **Benefit:** Improves performance for a common access pattern by storing all related data in one record.
    *   **When to Use:** Only when the number of repeating items is **known, static, and small** (e.g., a max of 3 phone numbers).

6.  **Step 7.6: Creating Extract Tables**
    *   **Example:** For a frequently run, complex report that joins many tables, create a separate, highly denormalized table containing exactly the data the report needs.
    *   **Benefit:** Dramatically speeds up the report by pre-joining and aggregating data.
    *   **Usage:** The extract table is typically populated overnight in a batch process. The data can be a few hours old (non-current).

7.  **Step 7.7: Partitioning Relations**
    *   **Definition:** Decomposing large tables/indexes into smaller, more manageable pieces.
    *   **Horizontal Partitioning:** Distributing **rows** based on a value (e.g., partitioning `ArchivedPropertyForRent` by `branchNo`).
    *   **Vertical Partitioning:** Distributing **columns** (e.g., splitting frequently accessed columns from rarely accessed ones, duplicating the primary key in both partitions).
    *   **Benefits:** Improves load balancing, performance, availability, recovery, and security.
    *   **Drawbacks:** Adds complexity for queries that need multiple partitions and can sometimes reduce performance for those queries.

**Maintaining Integrity:** Denormalization requires robust methods to maintain data consistency:
*   **Triggers:** The best method to automatically propagate updates to duplicated data.
*   **Transactions:** Ensure updates to multiple locations are atomic.
*   **Batch Reconciliation:** Periodically run jobs to clean up inconsistent data.

**Documentation:** All denormalization decisions, including the justification and method for maintaining integrity, must be thoroughly documented. The logical data model should be updated to reflect these changes.
